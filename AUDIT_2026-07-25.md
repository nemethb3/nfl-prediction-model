## AUDIT TASK 2: Weak Points & Bottlenecks

**Summary**: The project's honest, validated weak points cluster into three categories: (a) known-and-accepted (compression, game-level accuracy — already extensively documented in PROGRESS.md with real numbers), (b) genuinely fragile (near-zero error handling anywhere outside `data_pipeline.py`), and (c) real data-quality risks that haven't caused visible problems yet but would on the next edge case (single-QB/no-backup teams, the DL "2TM"/"3TM" PFR issue, ID scheme mismatches).

**1. Correlation/accuracy review** — a consolidated table pulling every "didn't validate" or "weak" finding actually recorded in PROGRESS.md this session, not a partial list:

| Component | Result | Verdict |
|---|---|---|
| WR SOS adjustment | NO HELP (both before and after the ref_season fix) | Never validated, never used in production |
| RB SOS adjustment | Actively hurts | Confirmed twice, never used |
| CB pass-rush synergy | No real signal (below noise floor) | Not used |
| S pass-rush synergy | Real but fails 2024 holdout | Not used |
| CB team-avg blended_score (bottom-up defense) | **-0.282** (negatively correlated) | The "shutdown corners get low volume" inversion — a real, structural measurement problem, not just weak signal |
| Coach quality | Good face validity, split-half reliability ≈0 (even negative for defense) | Confirmed not persistent, correctly never used forward |
| Bottom-up defensive composite (all 4) | -0.064, EDGE+LB only -0.015 | Loses to the top-down model despite stronger individual EDGE/LB signals — a genuinely counterintuitive, verified finding |
| Team offensive_strength (production) | +0.327 (post all fixes) | Real, but well below the +0.454 best-known formula (see below) |
| Game-level spread correlation | +0.257 (train), +0.255 (2024 holdout) | Modest — expected, single games are much noisier than season totals |
| Win projection backtest (season totals) | 0.216-0.224 across every variant tried | Weak, and **essentially insensitive to every fix made this session** — QB SOS bug fix, baseline-QB switch, none of it moved this number more than ~0.01 |
| Team strength compression | 3.34-3.36x too tight (best variant: full-roster depth at 2.39-2.41x) | Confirmed root cause of the win-projection weakness — even Vegas itself is compressed 1.6x, so ~half the gap may be structurally unavoidable |
| Game-level compression | Spread std 1.10 pts vs. real residual std 14.04 pts | Confirms the same compression pattern shows up at the game level too, not just season level |
| Edge detection | 0 edges found (confidence never exceeds 0.11 across 53 real games) | Direct, mechanical consequence of the above — not a separate bug |

**The single most important pattern in this table**: nothing tried this session — SOS bug fix, baseline QB switch, optimized multi-position weights, full-roster depth, combining approaches — moved the season-level win-backtest correlation off ~0.22, and nothing has meaningfully attacked the compression problem except full-roster depth (2.39x, still short of Vegas's 1.6x). **Every fix so far has been a methodology correction, not an accuracy improvement.** That's worth internalizing before Phase 5: the ceiling problem here isn't a bug waiting to be found, it's compression, and only one approach tried (full-roster) has moved that needle at all.

**2. Single points of failure** — verified, not assumed: grepped `try:` across every `src/*.py` file. **Result: 2 occurrences, both in `data_pipeline.py`'s `_fetch_with_fallback`.** Every other module — all model training, all PBP scans, all file reads, the entire game prediction engine, the entire weekly update pipeline — has zero error handling. Concretely:
- If `nflreadpy`/`nfl_data_py` is down or a season argument is out of range: `data_pipeline.py`'s bulk fetch degrades gracefully to year-by-year with skip-and-warn. Everything else that touches these libraries (the Prep Task's direct `nflreadpy` calls, the 2026 schedule pull) has no such fallback — a transient network failure would just crash with a raw traceback.
- If a `models/*.pkl` file is missing or corrupted: `load_epa_model()` does a bare `pickle.load()` — no existence check, no corruption handling. Every downstream function that calls it (OL, SOS, availability, synergy, Task 4's weight optimization, the game engine) would crash with an unhandled `FileNotFoundError`/`UnpicklingError`, not a clear message about which model is missing.
- If one position's projection CSV fails to generate: every aggregation function (`build_offensive_team_strength`, `build_depth_scenarios`, `combine_availability_and_optimized_weights`, etc.) does a bare `pd.read_csv()` with no existence check — a missing file crashes the whole pipeline rather than degrading (e.g., falling back to 3 positions instead of 4).
- **This is a real, unaddressed risk for Phase 5's "weekly automated pipeline" plan** (PROGRESS.md Phase 5 is still unstarted) — an unattended weekly cron-style run with zero error handling anywhere will eventually hit a transient failure (a 404 for a not-yet-published week, a malformed row) and crash silently or loudly with no operator-friendly signal about what broke or how to recover.

**3. Data quality issues** — checked directly, not assumed:
- **Team name consistency: verified clean.** `team_strength_2025.csv`'s 32 teams are an exact subset of `schedules_2015_2025.csv`'s team codes; the only difference is `schedules` additionally contains `OAK`/`SD`/`STL` (Raiders/Chargers/Rams' old codes, pre-relocation) — expected, not a bug, since team_strength only covers current-era teams.
- **ID scheme mismatch: real, already partially worked around, not fully resolved.** `player_id` (gsis-style) vs `pfr_id`/`pfr_player_id` (PFR-style) is a genuine two-ID-system split in this data. `player_metadata.csv` bridges them for most cases, but the DL "2TM"/"3TM" phantom-team bug (PROGRESS.md Task 3.1) is a direct symptom of this crosswalk being incomplete for traded players — currently patched with an 8-row filter-and-drop in `team_aggregation.py`, explicitly flagged in that file's own comments as needing a real fix in `data_pipeline.create_defense_season_stats`, never done.
- **Missing values in key columns**: not systematically audited in this pass — flagging as a real gap in this audit itself (see Recommendations).

**4. Untested assumptions:**
- **Edge case: teams with no real backup.** Verified directly this session (Task 3): only 13/32 teams have a real 2nd-QB clearing the min-opportunities threshold; the other 19 fall back to a league-average backup value. This is handled (not a crash risk), but it means the "backup_only" and "availability_adjusted" scenarios are, for the majority of teams, blending real data with a synthetic league-average stand-in — worth remembering when interpreting those numbers per-team, not just in aggregate.
- **Untested across years**: the `estimate_prior_weeks=3` constant (weekly update pipeline) was derived from exactly one season (real 2025) at three checkpoints. It has never been checked against 2024, 2023, etc. — a single-season-derived constant with no cross-year robustness check, the same category of risk this project has otherwise been careful to avoid (e.g., Task 4's stepwise weights were validated on a real, independent holdout).
- **Guessed-and-never-fixed constant, found today**: `BLEND_RATIO_BY_POSITION` (CB/S/LB tackle-vs-leverage blend ratios) is defined identically in `team_aggregation.py` and `phase3_diagnostic.py`, but `sos_adjustment.py`'s copy is **missing the LB entry entirely** — a real, verified divergence between three copy-pasted constants (see Technical Debt table).

**5. Scaling issues:**
- **Adding a new position (e.g., K, P)**: `POSITION_MAP` in `data_pipeline.py` already recognizes K/P/LS but no downstream model, adjustment, or aggregation function has a path for them — would require building an entire new position model from scratch, not a config change.
- **Memory**: every PBP-scanning function in this codebase (10+ of them across `coach_quality.py`, `team_strength.py`, `ol_quality.py`, `weekly_predictions.py`, `player_impact.py`) independently re-implements the same chunked-read pattern over the same 1.3GB file. Running many of them in sequence (as this session did repeatedly) means dozens of full-file scans — functionally fine (each one is memory-safe individually) but a real, verified performance cost (the weekly update demo alone took several minutes for ~30 scans).
- **Weekly update latency**: `weekly_predictions.py`'s `compute_team_epa_through_week()` re-scans the full 1.3GB PBP file every time it's called, even though only one season's early weeks are needed. At real weekly cadence in-season this is wasteful but survivable (once/week, not once/second) — worth optimizing before Phase 5's live pipeline if this function runs on any tighter schedule.

## AUDIT TASK 3: Architectural Clarity

**Summary**: The project has real design discipline within each module (thorough docstrings explaining *why*, not just what — a strength observed all session) but real DRY and file-organization debt at the project level: one constant is defined three times with a verified divergence, `win_projection.py` has become a 580-line catch-all covering five unrelated jobs, and the README doesn't reflect the current architecture.

**1. Is the design clear?**
- A new reader would need more than 10 minutes — there's no single data-flow document; PROGRESS.md is a chronological task log (excellent as a decision record, not organized as an architecture map), and README.md (57 lines) describes the *original 8-step plan* accurately but doesn't mention: the D: environment migration, `nflreadpy`, the 2026 rebuild, the existence of 6+ team-strength formula variants, or that `win_projection.py` now also does game predictions and Vegas edge detection.
- Docstrings are consistently strong at explaining *why* a design choice was made (this is a genuine, verified strength — nearly every function in `sos_adjustment.py`/`team_aggregation.py`/`win_projection.py` explains the reasoning, not just the mechanics). The weakness is at the *system* level, not the function level.

**2. Is it maintainable?**
- **Confirmed DRY violation with a real divergence**: `BLEND_RATIO_BY_POSITION` is copy-pasted in `sos_adjustment.py` (line 412), `team_aggregation.py` (line 57), `phase3_diagnostic.py` (line 58) — and the three copies have already drifted (`sos_adjustment.py`'s is missing `"LB"`). If anyone changes CB/S/LB's blend ratio in one file expecting it to apply everywhere, it silently won't.
- **EPA→points conversion touches 2 places** now: `win_projection.py`'s season-level `fit_final_model()` and its separate game-level `fit_game_level_epa_to_points()` — these are legitimately different granularities (season vs. game), not accidental duplication, but worth documenting clearly since both live in the same file under similar names.
- **`win_projection.py` is doing five distinct jobs** in one 580-line file: season win projection, backtest comparison, the game prediction engine, Vegas game-level comparison, and edge detection. This grew organically (each Subtask appended to the same file) and is now a genuine "which function do I need" navigation cost.
- **QB's canonical column choice** (baseline vs. SOS-adjusted) is now a parameter (`qb_canonical_col`) threaded through 4 different functions in `team_aggregation.py`, each with its own default and its own docstring explaining the same underlying finding. This works, but the same fact (SOS doesn't validate for QB) is now documented in 4 separate places rather than one shared constant/comment.

**3. Is it testable?**
- **Rigorous validation**: every position model, every adjustment layer (OL/SOS/availability/synergy), the EPA→wins conversion, and the game-level EPA→points conversion all have real holdout backtests against actual outcomes — this is a genuine, consistent strength of the whole project.
- **No validation at all**: nothing in this codebase has a unit test in the conventional sense (no `pytest`/`unittest` files exist anywhere in the repo — confirmed, no `test_*.py` files found). All validation is empirical/statistical (holdout correlation, real-outcome MAE), not correctness testing (e.g., nothing verifies `build_team_opponents()` returns the right *shape* independent of whether the resulting model happens to correlate well — the Task A empty-2026-schedule bug this session, which silently produced all-NaN SOS columns, is exactly the kind of thing a basic shape/null-count assertion would have caught before it needed a manual eyeball check).
- **No integration tests**: nothing automatically verifies the full pipeline runs end-to-end without manual, ad hoc `python -c "..."` invocations (which is how literally every task this session was actually executed and verified).

**4. Is it reproducible?** — **this is the audit's most severe finding; see Technical Debt #1.** Beyond that:
- Random seeds: `random_state` appears 11 times, confined to `player_models.py` and `sos_adjustment.py` — the actual randomized model classes (XGBoost). Ridge/LinearRegression (used elsewhere) are deterministic and don't need seeding, so this is actually fine, not a gap.
- Dependencies: `requirements.txt` uses loose `>=` version floors throughout, not pins — real risk given this session already needed a completely different data-fetching library (`nflreadpy`) to route around `nfl_data_py`'s endpoint gap; a loose floor doesn't protect against a future breaking change in any of these libraries.
- **`requirements.txt` changed silently this session** (`nfl-data-py>=0.33.0` → `>=0.3.3`, `matplotlib` added) — the `matplotlib` addition is correct and overdue (it's genuinely imported in `utilities.py` and was previously unlisted), but the `nfl-data-py` version floor change wasn't a deliberate action taken in this conversation — worth confirming this reflects intent, not an artifact of environment tooling.

## AUDIT TASK 7: System Diagram & Integration Check

**Data flow (text diagram):**

```
RAW INPUTS
  nflreadpy/nfl_data_py ──► data/raw/*.csv (pbp, schedules, weekly/seasonal stats, snap counts, PFR defense)
  Vegas lines ──────────────► embedded in schedules_*.csv (spread_line/total_line/moneylines)

CLEANING (data_pipeline.py)
  raw/* ──► player_metadata.csv, player_season_stats.csv, player_weekly_stats.csv,
            player_season_defense.csv, league_averages_by_position.csv

FEATURE ENGINEERING (utilities.py)
  processed player_*_stats + schedules ──► player_features_with_history.csv, age_curves_by_position.pkl

POSITION MODELS (player_models.py, trained once, applied via predict_next_season at any ref_season)
  features + season_stats ──► models/*.pkl ──► {position}_epa_projections_{year}.csv (offense)
                                            ──► {position}_{blended/war/sacks}_projections_{year}.csv (defense)

ADJUSTMENT LAYERS (ol_quality.py, sos_adjustment.py — all read+rewrite the projection CSVs in place)
  + team_ol_metrics (player_impact.py output, PBP-derived)
  + team_defense_epa splits (team_strength.py)
  ──► adds ol_modifier, opponent_sos, availability_factor, synergy columns to each projection CSV

AGGREGATION (team_aggregation.py — 6 competing formula variants, all converging on team_strength_2025/2026.csv)
  projection CSVs + play_mix + defense projections ──► team_strength_{year}.csv (+ 15 experimental variants)

WIN PROJECTION (win_projection.py)
  team_strength_2025.csv ──► EPA→wins regression ──► win_projections_2025.csv ──► backtest vs. actual_wins_2025.csv
  team_strength_2026.csv ──► EPA→points regression ──► game_predictions_2026_preseason.csv ──► Vegas comparison

WEEKLY UPDATE (weekly_predictions.py, validated on 2025, not yet connected to game_predictions_2026)
  team_strength_{year}.csv + partial-season PBP ──► team_strength_{year}_after_week{N}.csv
```

**Feedback loops**: **there currently are none, wired.** The weekly update pipeline produces `team_strength_2026_after_weekN.csv` but nothing reads that back into `build_game_prediction_engine()` to regenerate remaining-week predictions — that wiring (explicitly part of the original Subtask 2 spec's intent) doesn't exist yet. This is worth being direct about: the pieces are individually built and validated, but "weekly update → new game predictions" is not yet an automatic pipeline, it's two separately-callable functions a human would need to chain manually.
