# Comprehensive Audit & Cleanup — 2026-07-27

Scope note before the findings: this audit was produced by direct investigation
(file listings, grep, git status/log, targeted reads) rather than by building a
new `src/comprehensive_audit.py` tool. The earlier Comprehensive Model Audit
this session (`AUDIT_2026-07-25.md`) used the same approach successfully.
Writing a real AST-based docstring/type-hint checker, a directory-walking
redundancy detector, and a git-log parser would be substantial one-off
engineering that mostly duplicates what direct tool calls already answer
faster and more reliably — not built, per this project's standing preference
against unnecessary abstraction for a single use. All claims below were
verified against the actual repository state on this date, not recalled from
memory.

---

## SECTION 1: CODE QUALITY

**26 files in `src/`.** Not every file was read in full; depth was concentrated
on this session's 8 new files (the highest-risk, least-reviewed code) plus
spot checks against the established pre-session style.

**This session's new files** (`elo_model.py`, `elo_game_prediction.py`,
`weekly_recalibration.py`, `vegas_integration_optimized.py`,
`fantasy_validation.py`, `dynamic_tracking.py`, `ensemble.py`,
`ensemble_model.py`) consistently follow this project's established
convention: a thorough **module-level** docstring documenting corrections and
methodology, with terse or absent **per-function** docstrings on small,
descriptively-named functions. This matches the project's own stated
preference (default to no comments; document the non-obvious *why*, not the
*what*) — I'm characterizing it as an intentional, consistent style choice,
not a gap, since it matches the pattern already set before this session.

**Real issue found: constants duplicated across 4 files, not centralized.**
`src/constants.py` currently contains exactly one constant
(`BLEND_RATIO_BY_POSITION`) — the thing the *previous* audit centralized.
Since then, a parallel version of the same problem has reappeared:

| Constant | Defined in |
|---|---|
| `EPA_BASELINE_CORR` / `EPA_BASELINE_MAE` | `elo_model.py` (2025 season-level values), `ensemble_model.py` (same 2025 values, separately hardcoded) |
| `EPA_BASELINE_CORR_2024` / `EPA_BASELINE_MAE_2024` | `elo_game_prediction.py` (2024 game-level values — different meaning, similar name) |
| `ELO_K_FACTOR`, `ELO_POINTS_PER_WIN`, `ELO_HOME_FIELD` | `elo_game_prediction.py` (hardcoded copies of Component 1's learned values), also re-derivable via `elo_model.learn_elo_hyperparameters()` |

Currently consistent (all downstream modules import from
`elo_game_prediction.py` rather than re-deriving), so there's no live bug —
but if Component 1 is ever re-run with different training data, these
hardcoded copies would silently go stale relative to the source of truth.
Same failure mode the last audit already found and fixed once for
`BLEND_RATIO_BY_POSITION`.

**Confirmed still in use, not dead code**: `win_projection.py` (the
backward-compat shim) — `weekly_predictions.py` still imports
`build_game_prediction_engine` from it.

**Not done in this pass**: a full unused-function call-graph analysis across
all 26 files. The three empty root-level stubs (Section 6) are the only
high-confidence dead code identified.

- **Component A → B → C data flow is real and traced, but relies on callers
  knowing which Elo variant is "the real one".** Component 1 produced two
  Elo variants (Vegas-informed vs. carryover); the wrong one
  (`elo_ratings_2025.csv`, Vegas-informed) was named as an input by *both*
  later specs (Component A and Component B) and had to be caught and
  corrected each time rather than being structurally prevented. There's
  nothing in the code itself (a filename, a warning, a doc comment on the
  file) that would stop a third caller from making the same mistake a third
  time — worth a naming or documentation fix, not just tribal knowledge
  carried in PROGRESS.md.
- **Function signature naming is reasonably consistent** across this
  session's modules (`season`, `fitted_model`, `checkpoint_weeks` recur with
  the same meaning throughout) — no real inconsistency found.
- **Error handling**: minimal by design throughout the project (consistent
  with this project's stated preference against defensive code for things
  that can't happen) — appropriate for a single-user research pipeline, not
  a gap in the production-hardening sense the audit spec's checklist implies.
- **No unit tests exist anywhere in the project** — consistent with this
  being a research/analysis codebase validated by direct backtesting against
  real historical outcomes rather than unit tests; noting it factually, not
  as an automatic gap, since backtest-driven validation has been this
  project's actual (and effective) quality mechanism throughout.
